## 一、根因诊断：为什么「不知道要干嘛、怎么用」

不是缺功能。`docs/product.md` §2.2 列出的 34 条路由、5 个分区、4 个表面**全部已接线**。
难用的原因是**结构性错配**，共五条，每条都有代码或数据证据。

### 根因 1 · 内容规模与界面规模严重错配（最主要）

真实库实测（`C:\Users\51967\.memory-ops`，2026-11-17）：

| 项 | 实际数量 | 界面上对应的元素 |
|---|---|---|
| 记忆条目 | **3 篇** | 5 个分区 |
| INBOX 记录 | **3 条** | 34 条路由 |
| 未命中 | **5 条** | 首屏 5 个 KPI 格 |
| 维护作业 | 5 个子页签（修补/锚点/减重/爬升/复盘） | 0 条数据可处理 |
| 导出 | 4 个按钮 | — |
| 域 | 2 个（personal 2 篇 / work/dsh-config 1 篇） | — |

**3 条内容配 34 条能力**，于是每个页面都长得像「功能演示」：有控件、有数字、没有东西。
用户打开面板看到的是「待你处理 0 / 命中率 — / 过期率 0% / 维护作业 5 个入口」——
**全是空转的仪表，没有一句话告诉他现在该做什么。**

> 这不是「等数据多了就好」。产品第一指标是「常驻前缀 361 tokens / 请求」，
> 它的设计目标恰恰是**库里东西少**。一个为「少」而设计的产品，
> 界面必须为「少」设计——现状的界面是为「多」设计的。

### 根因 2 · 一级导航按「数据表」划分，不按「用户要干的事」划分

现状 5 个分区：**本项目 / 记录流 / 记忆 / 未命中 / 总览**。

这五个都是**系统内部的数据对象**，不是用户的意图。证据是它们互相重叠：

| 重叠 | 证据 |
|---|---|
| 「本项目」与「记忆」显示同一份东西 | `panes/memory.ts:39-53` 的注释自己承认：「记忆页签和本项目显示的是同一份东西」，修法只是加了个 `scope` 开关 |
| 「总览」也能拍板 | `overview.ts:205-233` 有确认/驳回/再留按钮，与「本项目」的 `QueueCard` 完全重复 |
| 「未命中」在三个地方出现 | 独立分区 + `project.ts:146-168`（本项目内）+ `overview.ts:242-249`（待你处理汇总） |

同一个动作有 3 个入口、同一份数据有 2 个页面——用户**无法建立心理模型**：
「我该去哪个页签做这件事？」每次都要重新推理。

### 根因 3 · 首屏第一屏没有一个「现在该做什么」

打开面板默认落在「本项目」。这一屏从上到下是：

1. KPI 4 格（相关记忆 / 待你处理 / 命中率 / 本项目索引）
2. 本项目索引文件列表
3. 未命中补齐（可能为空 → 整块不渲染）
4. 待你处理（可能为空 → 整块不渲染）
5. 分组标题 + 条目卡片

当队列为空时，第 3、4 块整个消失，**首屏只剩 KPI 和几张卡片**。
用户看到的是「数字 + 列表」，没有任何引导语、没有主动作按钮、没有下一步。

> 对比：队列为空本该是**最需要说话**的时刻（「你目前没有待办，可以考虑补这 5 条未命中」），
> 结果它是最安静的时刻。

### 根因 4 · 用户语言与系统语言混用

界面上同时存在两套词汇，且没有对照：

| 界面上的词 | 用户是否能懂 | 出处 |
|---|---|---|
| 该补了 / 观察中 / 草稿待确认 / 验证期内 / 已验证生效 | ❌ 内部状态机名 | `misses.ts:18-24` |
| 爬升 / 减重 / 锚点校验 / 修补 | ❌ 内部作业名 | `maintenance.ts:66-72` |
| 常驻前缀 / 索引层体积 / 本项目索引 | ❌ 三个数字含义不同，名字却很像 | `overview.ts:120-147` |
| 记账（命中记 cite，未命中记 miss） | ❌ 直接暴露事件流实现 | `memory.ts:189` 搜索框 placeholder |
| `G1 用户直述可豁免` | ❌ 内部闸门编号 | `project.ts:277`, `memory.ts:401` |
| `按需触发，无常驻定时器` | ❌ 实现细节，用户不需要知道 | `maintenance.ts:76` |
| `检索会记账，过滤不该记账` | ❌ 把设计决策当说明文字 | `memory.ts:256` |

`placeholder: '检索正文，回车记账（命中记 cite，未命中记 miss）…'` 是最典型的例子：
输入框的提示语应该是「搜什么」，这里写的是**系统的内部记账规则**。

### 根因 5 · 视觉层级失效：11 种字号 + 全站卡片

`styles.ts` 用了 10 / 10.5 / 11 / 11.5 / 12 / 13 / 14 / 15 / 16 / 17 / 18 共 **11 种字号**，
其中 10.5 与 11 与 11.5 相差 0.5px 肉眼不可分。同时 `.dmo-card` / `.dmo-kpi` /
`.dmo-budget` / `.dmo-session-kpi` 全部是 `border-radius: 8` + 同一套边框，
**所有区块视觉重量相同**，陌生人无法判断该先看哪里。

## 二、v4 的解法：一句话

> **把「数据分区」换成「任务入口」，首屏只回答一个问题：你现在该做哪件事。**

### 设计原则（三条，按优先级）

1. **规模自适应**：内容少的时候，界面必须**主动说出下一步**，而不是显示空仪表。
   → 引入「当前状态 → 建议动作」的单一引导，空态不是灰字而是一个可点的动作。
2. **一个动作只有一个入口**：任何写操作在全局只出现在一个页面（除详情页的上下文化重复）。
   现状「确认」有 3 处入口 → v4 收敛到 1 处（待办），详情页保留 1 处上下文入口。
3. **术语翻译**：内部状态机名一律不出现在界面；全部换成用户语言（见 §四 术语对照）。

## 三、新信息架构

### 3.1 一级导航：5 个任务入口（替代 5 个数据分区）

| 新入口 | 回答用户的问题 | 承接的旧分区 | 核心动作 |
|---|---|---|---|
| **今天** | 「我现在该干点什么？」 | 本项目 + 总览（待办部分） | 处理待办 / 记一条 / 补未命中 |
| **记一条** | 「我有个想法，赶紧存」 | 记录流（捕获部分）+ 快速捕获 | 写入 INBOX（1 步） |
| **待办** | 「有哪些事情压着？」 | 记录流 + 待你处理队列 + 未命中 | 流转状态 / 提升 / 拍板 / 补库 |
| **记忆** | 「我到底存了什么？」 | 记忆（全库） | 浏览 / 检索 / 编辑 / 退役 |
| **库健康** | 「这套系统健康吗、贵吗？」 | 总览（指标部分）+ 维护作业 | 看成本 / 跑维护 / 导出 |

**关键变化**：
- 「本项目」**不再是独立页签**，降级为「记忆」页里的一个筛选器 + 「今天」页的一个语境标题。
  理由：项目只是记忆的一个维度，把它升成一等导航导致与「记忆」重复（根因 2）。
- 「未命中」**不再是独立页签**，并入「待办」——因为「库里没有、需要你补」就是一件待办。
  理由：现状它在 3 处出现，用户不知道去哪（根因 2）。
- 「总览」拆成两半：「今天」拿走向用户的部分（待办），「库健康」拿走给系统看的部分（成本/维护）。
  理由：现状总览一页塞了 KPI + 预算 + 待办 + 三率 + 健康 + 域统计 + 维护 + 导出共 8 类内容。

### 3.2 层级与关系

```
记忆库面板（侧栏）
├── 今天                 ← 默认落地页，唯一"引导页"
│   ├── 一句话结论（现在处于什么状态）
│   ├── 主建议卡（唯一主动作，最多 1 个）
│   ├── 快速捕获（常驻，1 步写入）
│   └── 三条次要线索（待办 N / 未命中 N / 最近改动）
├── 记一条               ← 独立页面（兼容旧「记录流」的完整捕获能力：多行、类型、批量）
├── 待办
│   ├── 分三段：拍板 · 流转 · 补库（对应三种真实待办）
│   └── 每段空 → 段落整体隐藏，不显示 0
├── 记忆
│   ├── 列表（全库，可按域/状态/项目筛选）
│   └── 详情（证据链 / 编辑 / 退出）
└── 库健康
    ├── 成本（常驻前缀 361 / 索引层 286 分开看）
    ├── 维护作业（5 项，收起）
    └── 导出
```

### 3.3 关键路径：核心动作 3 步内可达

| 核心动作 | 旧路径 | 新路径 | 步数 |
|---|---|---|---|
| 记一条想法 | 打开侧栏 → 找右侧栏 tab / 敲 `/remember` → 输入 → 提交 | 打开面板 → 首屏输入框直接打字 → `Ctrl+Enter` | **1**（无需切页） |
| 处理一条待确认 | 打开面板 → 本项目 → 找到队列卡 → 确认 | 打开面板 → 首屏建议卡「确认」 | **1** |
| 补一条未命中 | 打开面板 → 未命中 → 找「该补了」→ 写结论 → 确认 | 打开面板 → 待办 → 补库段 → 写结论 → 确认 | **3** |
| 查某条记忆 | 打开面板 → 记忆 → 输入 → 回车 → 点卡片 | 打开面板 → 记忆 → 输入 → 回车 → 点卡片 | **3**（不变，已达标） |
| 退役一条 | 打开面板 → 记忆 → 点卡片 → 归档 | 打开面板 → 记忆 → 点卡片 → 归档 | **3**（不变） |

> 旧路径「记一条」之所以慢：`panel.ts` 的 5 个分区里**没有一个能记一条**——
> 「记录流」能记但用户不知道那是捕获页（名字叫「记录流」，像只读的日志）。
> 面板默认落在「本项目」，那里没有任何输入框。

## 五、逐页任务与四态处理

**四态 = 空 / 载 / 错 / 成**。每页都必须显式覆盖，不能默认 happy path。

> **「成」的定义（第 1 轮评审后裁定，消除文档歧义）**：
> 它不是一个独立的空白页面，而是**一次真实动作成功后的就地反馈状态**。
> 所以它在验收控制台里是一个可切换项（注入一条真实动作结果再渲染），
> 走的路径与用户点按钮完全相同，而不是另画一个「成功页」。
>
> 为什么不做成独立页面：本仓出过一次事故——`docs/product.md` §13.1 记录
> 「用户输入 `/remember` 后界面没有任何变化」。成功态的价值在于
> **证明动作生效**，不在展示一个静态页。

原型里每页都有「状态」开关（正常 / 加载中 / 空 / 出错 / 成功），可直接切换验收。

### 5.1 今天（默认落地页）

- **唯一核心任务**：让用户在 1 秒内知道「现在该做哪一件事」，并能一键做掉。
- **首屏结构**：一句话结论 → 唯一主建议卡 → 常驻捕获框 → 三条次要线索。

| 态 | 处理 |
|---|---|
| 空（库全空） | 结论改为「这是你的第一条记忆」；主建议卡 = 写第一条（聚焦捕获框）；次要线索整块隐藏 |
| 空（有内容但无待办） | 结论 = 「没有待办。库里 3 条，最近一条 1 天前」；主建议卡切换为最高价值的可做项（有未命中 → 「补这 1 条」；无则 → 「去记忆里逛逛」） |
| 载 | 结论行骨架 + 建议卡骨架（等高，不塌陷） |
| 错 | 「读不到记忆库：<原因>。**库文件没有丢，这是读取问题。**」+ 重试 + 「打开库目录」 |
| 成 | 做完任一动作后，结论行就地更新一行提示（例：「已确认 1 条 · 还剩 1 条待办」），不弹 toast 盖住内容 |

> 关键设计：**空态不是灰字，而是一个可点的动作**。这是根因 3 的直接解药。

### 5.2 记一条

- **唯一核心任务**：把一句话写进 INBOX，并让用户看到它真的进去了。
- 保留旧「记录流」的全部捕获能力（类型选择、多行拆条、批量、隐私拦截）。

| 态 | 处理 |
|---|---|
| 空（无历史） | 展示「这里会列出你刚记的」，不显示空表格 |
| 载 | 输入区始终可用（不等数据）；历史区骨架 |
| 错 | 写入失败：「没存上：<原因>。内容还在输入框里，可以重试」——**绝不清空输入** |
| 成 | 输入框下方就地出现「已存入 · 2 秒前 · 撤销」，并可继续写；不弹窗 |

> 隐私拦截是一个独立的错误子态：红条 + 说明「检测到疑似密钥，已拒写」+「填入脱敏版本」按钮。

### 5.3 待办

- **唯一核心任务**：把压着的事清掉。分三段，每段空则隐藏。
- 三段：**拍板**（推断待确认 / 待复核 / 到期）、**流转**（INBOX open/todo）、**补库**（未命中等你补）

| 态 | 处理 |
|---|---|
| 空（三段皆空） | 一整屏的「清空了」+ 一句话「下次 agent 搜不到东西时会自动出现在这里」+ 去记忆 |
| 部分空 | 空的段落**整体不渲染**，不显示「0 条」 |
| 载 | 三段各自骨架 |
| 错 | 每段独立报错 + 独立重试（一段失败不拖垮另两段） |
| 成 | 该条从队列中移除，段落标题计数 -1，就地显示「已确认」；队列清空时就地换成完成态 |

### 5.4 记忆

- **唯一核心任务**：找到某条记忆并处理它。
- 列表为**台账**（hairline 分隔，不是卡片），元信息等宽右对齐。

| 态 | 处理 |
|---|---|
| 空（全库 0 条） | 「库是空的」+ 去记一条 |
| 空（筛选后 0 条） | 「这个筛选下没有」+ **清空筛选**按钮（不是只说没有） |
| 空（检索 0 命中） | 「没搜到『xx』」+ 「把它变成一条待补」——检索落空本身就是补库输入 |
| 载 | 列表骨架 |
| 错 | 读取失败 + 重试；**说明库没坏** |
| 成 | 归档/确认后行内状态更新，不刷新整页 |

### 5.5 库健康

- **唯一核心任务**：回答「这套东西贵不贵、该不该维护」。
- 首屏只有两行数字：每请求成本 / 索引体积（含对比锚点），然后是维护作业（收起）、导出。

| 态 | 处理 |
|---|---|
| 空（无数据） | 成本显示「—」并解释「算不出来不等于 0」 |
| 载 | 骨架 |
| 错（读不到 skill） | 「读不到 skill 列表：<原因>。当前只统计到目录框架 N，**这个数字偏小**」——不许伪装成 0（沿用 §17.8② 教训） |
| 成 | 维护作业执行后就地显示结果行 |

## 六、与既有代码的对应关系（迁移安全性）

v4 **不删任何路由**。34 条路由全部保留，只是换入口：

| 旧分区 | 新位置 | 路由 |
|---|---|---|
| 本项目 | 今天（队列+条目）+ 记忆（项目筛选） | `snapshot` |
| 记录流 | 记一条（捕获）+ 待办（流转） | `inbox` `capture` `captureBatch` `updateInbox` `deleteInbox` `batchInboxState` `promoteInbox` |
