## 一、一句话产品

**「记忆库」是一套人机共读的个人记忆系统：人负责确认与退役，agent 负责按索引取用；两端共用同一份 Markdown 真相源。**

它不是笔记软件。判断依据来自同一份会话里已经付过学费的实测：

| 已发生的事实 | 产品含义 |
|---|---|
| mnemon 装了 11 个工具，`bodies total: 0` | 没有内容的通用记忆平台 = 纯租金 |
| knowledge 2.4 MB sqlite + 常驻 embedding 进程，收益不成正比 | 重型检索设施不能进这个产品 |
| 53 次配置变更作废 750 万 tokens 缓存 | 记忆结构必须稳定、只追加 |
| 每条记忆都随每请求前缀付费 | 成本必须是产品里的一等公民，不是运维细节 |

所以产品的主线不是「怎么记」，而是**怎么让几百 token 的索引换回多次命中，并让不命中的那些驱动补齐**。

## 三、三条产品主张

### 主张 1 · 成本可见

每条记忆显示：体积、token、所属层、被引用次数。
顶栏第一个指标不是「笔记数」，是**常驻前缀**，并给出对比锚点：「弃用的 knowledge 为 4,120」。

**三个数字必须分清（2026-11-05 实测，2026-11-06 复核）：**

| 数字 | 含义 | 付费方式 | 当前值 |
|---|---|---|---|
| **常驻前缀** | 两个 skill description（90 + 100）+ `<available_skills>` 目录框架（171） | **每请求付费** | **361** |
| **索引层体积** | 所有 `layer: l0` 文件之和（135 + 151） | 仅被 `read` 时 | **286** |
| **本项目索引** | 仅该项目 `layer: l0` 文件之和 | 仅被 `read` 时 | sz-web 151 / 无项目 0 |

> **为什么必须拆开**：按 286 去优化会去删索引表，那对每请求成本毫无影响；
> 真正该动的是 190 tokens 的 skill description。指标混在一起就无法指导决策。
> 详细更正记录见 §十二、§十四。

### 主张 2 · 可信度分级

三类严格分开，物理落在不同文件里：

| 层 | 装什么 | 写入条件 | 展示 |
|---|---|---|---|
| 事实 | 你说过的话 | 你说了才写 | 绿色标签 |
| 原则 | 你定的规矩 | 你确认才写 | 绿色标签 |
| **推断** | 从对话总结的模式 | **先问你，确认才落档** | 琥珀色「待确认」 |

推断错了会显得自作聪明，所以它必须可见、可驳回、且带出处日期。

> ✅ **实际状态（v3.4）**：确认、驳回、撤销驳回三者都有 UI 入口，见待处理队列与记忆详情。

### 主张 3 · 到期退役

90 天未被引用 → 标灰；134 天 → 进「待你处理」，给两个出口：归档到 `archive/`，或再留 90 天。
每个文件的目标上限是 80 行，超了**会被标出来并进复盘清单**，系统给出压缩与拆分建议。

> ⚠️ **它不是硬闸门**：超 80 行不会阻断写入、也不会拒绝保存。
> 早先文档写「硬上限，超了必须压缩」，那是措辞过强——代码只做标记与建议，
> 拦不拦到最后还是人的判断。这符合「人负责拍板」的产品立场，但别把它当成强制约束。

> 这是唯一能防止半年后变成第二个 knowledge 的机制。
> ✅ **v3.4 补上出口**：超限文件可在「总览 · 维护作业 · 减重」做**机械压缩**
> （去行尾空白 / 折叠空行 / 去首尾空行）。语义摘要与拆文件仍坚持人工，系统只给建议。

## 四、信息架构

```
L0 常驻层（每请求 361 tokens = 两个 skill description 190 + 目录框架 171）
   ├─ 关于我：偏好 / 原则 / 推断 / 目标 / INBOX      ← 由 description 指路，正文不在此层
   └─ 关于项目：结构 / 模块地图 / 坑 / 版本分析 / 台账
              ↓ 命中触发词
L1 索引层（只在需要时加载）
   我能查什么 + 该读哪个文件 + 记录规则
   实测：personal/index.md 135 + work/sz-web/index.md 151 = 286 tokens
              ↓ 命中具体条目
L2 详情层（单文件 2–16 KB，命中才读）
   实测：34 篇未标层（多为历史文档）+ 6 篇 l2
```

> **注意**：L0 装的是「索引的入口」（skill description），不是索引本身。
> 286 是 L1 索引层的实测体积，361 才是 L0 的每请求成本。

存储与索引分离（UI 读写不依赖 skill 安装位置）：

```
~/.memory-ops/                 ← 真相源，人可读、git 可管（与 ~/.dsh 同级）
├── personal/   INBOX identity principles preferences patterns goals + index
├── work/sz-web/  overview maps workflow issues dsh hnay meta + index
└── .state/     events.jsonl（append-only）+ misses.json

~/.dsh/skills/*-memory/SKILL.md  ← 纯索引，只有路径表（当前实际在 /Users/zeze/Desktop/dsh/skill/）
```

**两域物理隔离**：工作会话不会加载个人档案；个人会话不会加载 35 篇项目文档。

### 5.2 原设计原则（保留，但需按现状理解）

原设计写的是「能力必须全量对等，差异只允许在空间与操作方式上」。
**现状是单端**：只有插件端。Web 端是**待建**，不是「已完成」。

原「单向漏斗」教训仍然成立：插件端只做捕获 → 用户永远停在「记了 8 条、0 条拍板」。
所以插件端承担了全部写操作，这一点没有退让。

## 七、落地结构（实际）

```
packages/
├── core/                  TS · 零运行时依赖
│   ├── schema.ts          frontmatter + INBOX 五列（唯一契约）
│   ├── parse.ts           md ↔ 结构体
│   ├── store.ts           原子追加（tmp + rename + 文件锁）
│   ├── search.ts          全文检索（子串 + 词边界），无向量库
│   ├── privacy.ts         隐私闸门
│   ├── actions.ts         34 条能力的唯一实现
│   └── maintenance.ts     维护作业（修补 / 锚点 / 减重 / 复盘 / 爬升）
└── dsh-plugin/            DSH 插件
    ├── src/index.ts       host 入口
    ├── src/bridge.ts      34 条 HTTP 路由
    ├── src/tools.ts       memory_recall / memory_write
    └── src/client/        浏览器半体（4 表面）
        ├── panes/         5 个分区 + 维护面板
        ├── panel.ts       侧栏面板外壳
        ├── session-view.ts 会话记忆 tab
        ├── capture-tab.ts 右侧栏捕获
        └── remember.ts    /remember 弹窗
```

**为什么必须有 core**：INBOX 状态流转与统计口径一旦两端各写一份，
三个月后数字必然对不上。组件不共享（React / Vue 无法互通），逻辑必须共享。

### 数据契约（不可随意改）

```markdown
| 日期 | 类型 | 内容 | 状态 | 去向 |
```

- 类型枚举固定 5 个：`想法 计划 问题 待办 决策`
- 状态：`open → todo → done / dropped`
- 正文禁止裸 `|`，序列化时转义 `\|`
- 写入原子性：`tmp + rename`，避免 agent 与 UI 同时写出现半行
- 批量删行**从大行号往小删**，否则行号漂移

### frontmatter v2 字段（**已解析，但多数未写入**）

`confidence` / `status` / `evidence` / `anchor` / `superseded_by` / `origin` 六个字段
core **能读能写**，但：

- ✅ 实际在用：`status`、`confidence`、`evidence`、`origin`（由 `memory_write` 与状态机写入）
- ⚠️ 有字段无逻辑：`anchor`（只读展示，**无每日 02:10 校验作业**）、`superseded_by`（无冲突消解流程）

## 九、两个需要你拍板的决策

**① 工作域要不要从 skill 目录搬到 `~/.memory-ops/work/sz-web/`？**

架构上该搬（数据不该住在 skill 包里）。但搬迁必须同步改 `SKILL.md` 的路径表，
而 SKILL.md 的 frontmatter 属于常驻前缀——**一改就作废当前会话缓存**（实测单次 20–57 万 tokens）。

- 搬：一次付清，之后架构干净
- 不搬：UI 读 skill 目录，零成本，但插件与 Web 都依赖 skill 安装位置

> 精确说：作废缓存的是 frontmatter 里的 `description`（常驻前缀 190 tokens 的一部分），
> 正文路径表本身不在前缀里。但改路径表通常伴随改 description，
> 所以按「整份 SKILL.md 都算前缀」来保守估计是对的。

**② `personal-memory` skill 什么时候建？**

个人域数据已经躺好了，但没有 skill 索引，agent 不会主动去读。
建 skill = 改常驻前缀 = 又一次缓存作废。
建议同上：**与 ① 同一批执行**。

## 十、下一步最值得优化的点

**补上「驳回」入口。**

这不是功能补齐，是修正一个逻辑断裂：状态机里有 `rejected` 态、
有 30 天静默规则、有 `undoReject` 路由、有 5 项测试覆盖，

## 十一、v3 打磨：信任与失效的仪表（2026-11-05 设计）

> 动因：骨架（Markdown 真相源、成本可见、两域隔离、到期退役）是对的，
> 但一条记忆「凭什么可信、什么时候会失效、失效后谁处理」这条闭环缺失。

### 11.1 一句话

**用户要判断的不是「记了多少」，而是「哪条能信、哪条过期了、哪个问题还没被记住」。**

### 11.2 吸收了 7 项机制

| 机制 | 落法 | 实现状态 |
|---|---|---|
| 证据必填 | frontmatter `evidence[]` + 详情页证据链 | ✅ 已实现 |
| 置信度状态机 | `status` / `confidence`；队列徽标 + 详情 stepper | ✅ 已实现 |
| 驳回静默 | 驳回后 30 天不再注入，可撤销 | ✅ 待处理队列与详情都有入口 |
| 锚点失效 | `anchor{path,symbol,hash}` → stale 降权 | ⚠️ 字段与展示有，**校验作业无** |
| 四道闸门 | 写入来源记 `origin` | ✅ 已实现（G2/G3/G4 强制 evidence） |
| 隐私闸门 | 密钥 / 私钥 / 身份证 / 内网 IP 正则 | ✅ 已实现（捕获与改正文两处） |
| 预算与三率 | 三段预算硬顶 + 命中/确认/过期率 | ✅ 口径已实现；检索走 `search` 记账后不再恒为 null |

> **命中率为什么是 null**：它依赖 `recall` 事件，而唯一的检索入口
> `search` 路由未被 UI 调用（记忆分区用客户端过滤）。所以 30 天内没有 recall 事件，
> 分母为 0 → 返回 `null`。这是**诚实的结果**，不是 bug。

### 11.3 明确不吸收的四件事

| 拒绝 | 理由 |
|---|---|
| 向量检索 / embedding 常驻进程 | 检索已是子串 + 索引表，够用；向量库会把常驻成本拉回老路 |
| `storageDomain` per-record 存储 | Markdown 真相源是产品根基：可读、可 git、可手改 |
| 自动提取并直接写库 | 只生成草稿，人确认才落。**G2 每日 50 条 / 单会话 15 条熔断未实现**（只有「只进 INBOX」的语义约束，没有计数拦截） |
| 新增第五个表面 | 4 表面 + 5 分区是已实现的稳定结构，不扩张导航 |

### 11.4 数据契约 v2（向后兼容）

frontmatter 新增可选字段：`confidence` / `status` / `refuted_reason` / `evidence[]` /
`anchor{}` / `superseded_by` / `origin`。

统计口径从事件流派生，新增 `.state/events.jsonl`（append-only）：

```json
{"at":"2026-11-04T15:32:07+08:00","session":"web","kind":"recall","ids":["work.sz-web.issues.fake-empty"],"query":"面板空白"}
{"at":"2026-11-04T15:32:41+08:00","session":"web","kind":"cite","ids":["work.sz-web.issues.fake-empty"]}
{"at":"2026-11-02T09:24:00+08:00","session":"web","kind":"miss","query":"grep read"}
```

三率定义（写进 `store.summarize`，两端共用）：

| 指标 | 口径 | 目标 | 当前 |
|---|---|---|---|
| 命中率 | 30 天内 `cite` 条目数 ÷ `recall` 条目数 | > 60% | **0%**（recall 有、cite 从未产出；v3.5 已修，见 §17.10③） |
| 确认率 | 30 天内 `confirmed` ÷ (`confirmed` + `rejected`) | > 70% | null（无确认/驳回记录） |
| 过期率 | 自然月内 (`stale` + `archived`) ÷ 总条目 | 逐月下降 | 0% |

状态迁移（唯一合法路径）：

```
hypothesis ──跨会话重复≥2──> observed ──重复≥3且无反驳──> reinforced ──人确认──> confirmed ──> archived
   任意态 ──人驳回──> rejected（30 天静默，可撤销）
   任意态 ──锚点失效 / 90 天未命中──> stale（降权 0.4，仍可检索）──复核通过──> confirmed
```

> ✅ **v3.4 已实现自动爬升**：`planPromotions` 按「≥3 个**不同会话**引用」出计划，
> 默认 dry-run，人点一下才落库；最多爬到 `reinforced`，`confirmed` 与 `rejected` 永不自动改。

## 十三、v3.2 `/remember` 改为弹窗输入（2026-11-05）

### 13.1 动因

用户实测反馈：**输入 `/remember 内容` 回车后，界面上没有任何变化**。
输入框被清空、屏幕无提示、也不知道到底存没存。

这不是交互风格问题，是**可用性缺陷**：命令类交互必须给出可见的接手动作。
一个「做完了但看起来什么都没发生」的命令，比一个报错的命令更糟。

### 13.2 改法（照 `dsh-context` 的 `/context`）

| 步骤 | 做法 |
|---|---|
| 1. 交出发送权 | `onPick` / `matchEnter` 返回 `'handled'`，输入框清空 |
| 2. 置开状态 | per-session store 置为 `open` |
| 3. 渲染接手 | `conversation.input.overlay` 槽位里的对话框订阅该 store |

三种进入方式都落到同一个弹窗：

| 输入 | 行为 |
|---|---|
| 菜单里选 `/remember` | 打开弹窗，空内容 |
| 裸回车 `/remember` | 打开弹窗，空内容 |
| 回车 `/remember 内容` | 打开弹窗，**预填**内容，仍让用户确认 |

### 13.3 反馈闭环

存成功后弹窗关闭 + 浮层留提示（5 秒消失）：`已存入 personal/INBOX.md  [撤销] [×]`

- 撤销按**内容匹配最近一条**，不记行号——行号会因并发捕获漂移
- 隐私拦截时**不关闭弹窗**，框内解释原因并给「填入脱敏文本」按钮

### 13.4 上线后故障：回车被当普通消息发出去（同日修复）

两处接线 bug，都不在业务逻辑里：

| # | Bug | 后果 | 修法 |
|---|---|---|---|
| 1 | `'handled'` 包成了 `{kind:'handled'}` | 宿主不认识，落回默认发送路径 | 返回字符串字面量本身 |
| 2 | `ctx.get('inputTriggers')` 在 apply 时取值 | 服务延迟提供，此时 `undefined`，注册被静默跳过 | 改 `ctx.inject(['inputTriggers'], ...)` |

`PickOutcome` 是 `{claim} | {insert} | {text} | 'handled' | undefined`——
`'handled'` 是**字符串字面量**，不是可扩展对象。

### 13.5 为什么 12 项纯函数测试没拦住

因为它们测的是「解析对不对、store 通知几次」，而故障出在**注册是否接上宿主**。

补了 `test/wiring.test.mjs`（9 项）：用假 ctx 把 `registerRemember` 真跑一遍。
并做了反向验证——分别把两个 bug 改回去，测试分别红 3 项 / 8 项。

> **教训**：插件类代码的默认失败模式是**静默不生效**，不是抛异常。
> 所以「注册接线」必须单独测。

## 十四、v3.3 口径修正：项目视图的索引 ≠ 全库索引（2026-11-05）

### 14.1 错在哪

用户看到「本项目」分区也有「常驻前缀」一格，问：这个和总览的一样吗？
**用户是对的，代码是错的。** `snapshot` 用全量 entries 算 stats，
项目过滤只作用于条目列表、不作用于统计：

| 场景 | 修复前 | 实际 |
|---|---|---|
| 本项目 = sz-web | 286（全库） | 151 |
| 本项目 = 无记忆的项目 | **286** | **0** |

第二种最糟：界面同时出现「0 条记忆」和「286 tokens」，画面自相矛盾。

### 14.2 三层数字，各有归属

| 数字 | 含义 | 在哪看 | 当前值 |
|---|---|---|---|
| 常驻前缀 | skill description + 框架，**每请求付费** | 总览 | 361 |
| 全库索引层 | 所有 l0 文件，**按需加载** | 总览 | 286 |
| 本项目索引 | 仅该项目 l0 文件，**按需加载** | 本项目 | sz-web 151 / 无项目 0 |

为什么项目视图不显示「每请求付费」：**skill description 是会话级的，不是项目级的**。

### 14.3 落地

- `stats` 按过滤后的 entries 计算
- `queue` 同样跟着过滤（原来也是全量，同一类错误）
- 新增 `statsScope: 'all' | 'scoped'`
- 新增 `projectIndex`：列出本项目 l0 文件，让数字可追溯
- 本项目那一格改名「**本项目索引**」

### 14.4 教训

这类 bug 的共同特征：**过滤只作用了一半**。列表过滤了、统计没过滤；
数据过滤了、队列没过滤。而且它一直没被发现，是因为**总数看起来是对的**——
全量 286 确实等于 135 + 151。所以测试要断言「两个项目各自的数字」。

## 十七、v3.4 缺口补齐（2026-11-06）

> 动因：§2.3 那张「有路由、没入口」的表挂了两个版本。它不会让任何测试变红——
> 逻辑是对的，只是没人调用。这类缺陷能安静地活很久，所以本次既补功能，也补**接线测试**。

### 17.1 为什么不给维护作业加定时器

文档原先写的是「每日 02:10 作业」「每日减重 / 每周复盘」。本次落地改成**按需触发**，
理由与 §11.3 拒绝 embedding 常驻进程是同一条：

| 定时器要求 | 代价 |
|---|---|
| 进程要一直活着 | 与「零常驻成本」主张冲突 |
| 后台写盘 | 用户不看的时候库在变，与「只追加、可审」冲突 |
| 插件卸载要干净退出 | 多一条生命周期路径要维护 |

换来的是什么？只是「省掉手动点一下」。**不值得。**

所以四项作业都是纯函数 + 路由 + 按钮：什么时候跑由人决定，跑之前先看预览。

### 17.2 四项作业的边界

| 作业 | 做什么 | **明确不做**（写下来防以后「顺手」加上） |
|---|---|---|
| 锚点校验 | 比对 `anchor.hash` 与文件当前指纹、检查 `anchor.symbol` 是否还在 | 不自动改内容；`unverifiable` 不降级（缺数据不是证据） |
| 减重 | 去行尾空白 / 折叠连续空行 / 去首尾空行 | 不删重复行、不摘要正文、不自动拆文件（拆分会改路径 = 改记忆的 id） |
| 每周复盘 | 窗口内事件计数 + 行动项排序 | 只读，不改库 |
| 自动爬升 | ≥3 个**不同会话**引用 → 升一级 | 最多到 `reinforced`；`confirmed` 与 `rejected` 永不自动改；默认 dry-run |

> **「不同会话」才是规则本体**：同一会话里问三次，是被同一次困惑驱动的，
> 不构成独立验证。去掉这个限制，这条规则就退化成「计数」。

### 17.3 实测结果（真实库 `~/.memory-ops`，42 条目）

跑一遍四项作业的真实输出：

| 指标 | 值 | 怎么读 |
|---|---|---|
| 常驻前缀（每请求） | 171 | 无 skill 注入时只剩目录框架；注入两个 skill 后应为 361 |
| 索引层体积 | 314 | 与上者**不是同一个数**，这正是 §12 要拆开的原因 |
| 超限文件 | 14 篇 | 与 §四 的计数一致 |
| 减重可省 | **0 行** | ⚠️ 已在真实库执行过一次压缩，无损空间已用尽 |
| 可爬升 | 0 条 | 无跨会话引用记录，规则正确拒绝 |
| 带锚点条目 | 0 / 42 | 锚点功能从未被真实数据用上，所以 §17.4 那个 bug 一直没暴露 |

> **「0 行」这个数字值得单独记**：
>

> 再跑就是 0。这诚实地说明**「一键减重」不是万灵药**——14 篇各有 100–250 行，
> 机械压缩只能去掉空行和行尾空格，剩下的必须人工摘要或拆文件。

### 17.4 顺带修掉的两个既有 bug

**① `anchor` 字段写进去读不出来**

`serializeFrontmatter` 把对象写成块列表，`parseFrontmatter` 解析回来是**数组**；
而 `readEntry` 的判断是 `!Array.isArray(meta.anchor)`，于是**永远是 `null`**。

后果：锚点字段能写、能存、读不回来 → 展示与校验全部空转。
因为真实库 0 篇带 anchor，这个 bug 从 v3 潜伏到现在。
修法：`normalizeAnchor` 同时接受数组与裸对象（数组取第一项）。

**② KPI 把索引层冒充常驻前缀**

`overview.kpi.residentTokens` 取的是 `stats.layers.l0.tokens`（索引层 286），
而构成面板里写的是 `billedTokens`（每请求 361）。同一屏两个数字对不上。

按错的那个去优化会去删索引表，而索引表**不在每请求前缀里**——一分钱省不下来。
这正是 §12 专门记录过的坑，代码却还踩在上面。
修法：`residentTokens` 改取 `billedTokens`，索引层单列 `indexTokens` 一格，UI 两格并排。

### 17.7 数据契约与现实脱节的修复（续）

§17.4 修的是两个代码 bug。但用户反馈「不知道怎么用」之后，核对真实库发现**更严重的一层**：

**42 篇记忆里，34 篇没有 frontmatter、7 篇 `status` 是非法值 `active`。**

这不是代码 bug，是**数据契约与真实数据脱节**。后果是一串静默失效：

| 缺失字段 | 失效后果 |
|---|---|
| `status` | 读成 `active`（不在枚举内）→ `needsDecision()` 全部返回 false → **待你处理队列永远 0 条** |
| `layer` | 读成空串 → 预算账本 L0/L1/L2 三段全错 |
| `updated` | 读成空 → `expiryOf()` 拿不到基准 → 永远不提示到期退役 |

用户看到的现象是「插件装了、数据也在、但什么都不工作」。
**这不是用户不会用，是产品让他无从判断。**

落地：新增 `repairMeta` 能力（core `planRepair` 纯函数 + 路由 + 总览面板「修补」页签）。

三条硬规矩写进了实现：

1. **绝不改正文**——只写 frontmatter。实测 42 篇正文逐字节比对，0 篇有差异；
   ⚠️ 但**当时没验证 frontmatter 里的块列表**——§17.10 的 ② 就是补上这一维度：
   正文没变，标签却被毁。这条教训是「验证要比对自己以为改动的范围更宽」；
2. **绝不覆盖已有值**——只补空洞。唯一例外是非法 `status`（如 `active`），
   因为「保留非空值」会把脏值原样留下，修补完还在坏；
3. **不刷新 `updated`**——为此新增 `store.mergeMeta`（区别于 `patchMeta` 的强刷时间戳）。
   刷日期会伪造「刚更新过」，把 134 天退役倒计时偷偷清零。

修补后真实库状态：42 篇元数据完整、待拍板 **2** 条、确认率 **100%**、层统计 L0/L1/L2 = 2/3/37。

### 17.8 三处「看不明白」的界面修复（用户实测反馈）

用户装好后截图反馈三个问题。前两个是真 bug，第三个是设计缺失。

**① 「记忆」页签是空的，但库里有 42 篇**

`MemoryList` 把 `project` 直接传给了 snapshot，于是「记忆」和「本项目」
显示同一份东西——当前项目（memory-ops）确实没有专属记忆，两页都是 0 条。

这不是用户不会用，是**两页职责重叠**。修法：`Memory` 默认**全库**，
顶部加「全部记忆 / 仅本项目」下拉 + 域筛选下拉。
分工定死：「本项目」回答「这项目有什么」，「记忆」回答「我到底存了什么」。

> 这条同时推翻了 manual.md 初版的说法（当时写「记忆是全库列表」而代码不是）。
> 文档写错比代码写错更糟——用户会按文档去点，然后怀疑自己。

**② 常驻前缀展开后只有一个 171**

根因不是 UI，是宿主这一侧读不到 skill：

```ts
skills.list({ modelInvocableOnly: true })   // ← 本地 skill 不写这个标记，全被滤掉
```

`modelInvocableOnly` 把未声明该标记的 skill 全部滤掉，而 `/Users/zeze/Desktop/dsh/skill/`
下 5 个 skill 都没写。于是 catalog 恒为 0，`billedTokens` 只剩框架 171。

修法两处：
1. 去掉 `modelInvocableOnly`，改按「有 description」过滤；
2. 新增三态 `resident.state`（`ok` / `empty` / `error`）+ `skillsError` 原因串。
   **「读不到」不许伪装成「没有」**——否则用户会以为 171 就是全部，而真实值是 225。

**③ 预算账本看不懂、域统计不能下钻**

- 预算：原来只给「L0 常驻层 316 / 1024」，且**这个 316 是索引文件之和，
  而 KPI 的常驻前缀是 171**——同屏两个 L0 数字对不上。
  现在每段都带 `billing`（每请求 / 按需）+ `note` + `advice`，
  并把「索引文件合计」单列为 `L0*` 行，明确写「这数字大不代表贵」。
- 域统计：原来只给「sz-web 35 篇 / 63,030 tokens」，无法验证也无法下钻。
  现在每个域带 `entries`（按 tokens 降序），点域展开即见每一篇。

**新增测试（5 项）**锁住口径一致性：
- `预算账本 L0 与 KPI 常驻前缀必须是同一个数`
- `每一段预算都带 billing 与 advice`
- `域统计带明细，按体积降序`
- `skill 读取失败时 resident.state 为 error 并带原因`
- `读到 skill 时 state 为 ok，一个都没有时为 empty`

### 17.9 白屏事故：Hook 顺序被条件分支穿过（2026-11-06）

**现象**：左侧点开「记忆库」，整个面板一片空白。

**根因**：给「记忆」页签加域筛选时，把 `useState` 写在了 `if (phase === 'loading') return ...` **之后**：

```ts
const { phase, data } = useBridge(...)
if (phase === 'loading') return Skeleton(...)   // ← 首帧从这里返回
const [domainFilter, setDomainFilter] = useState('')  // ← 首帧被跳过
```

首帧走 loading 分支时这个 hook 被跳过；数据到达后再渲染，hook 数量从 6 变 7，
React 检测到顺序不一致 → 抛错 → 整片白屏。

**为什么三道防线都没拦住**：

| 防线 | 为什么失效 |
|---|---|
| `tsc --noEmit` | 语法完全合法，类型也对 |
| 单元测试 | 组件从未被渲染，只测了纯函数与路由 |
| 我之前的接线测试 | 只检查「有没有调用点」，不检查调用位置 |

**修法**：所有 hook 提到所有 early return 之前。

**新增测试**：`wiring-ui.test.mjs` 增加「Hook 顺序（白屏防线）」，按花括号配平解析每个
组件的函数体，断言**没有任何 hook 出现在 early return 之后**。

反向验证：把 `domainFilter` 挪回 early return 之后，测试立刻红在
`panes/memory.ts · MemoryList · 第 114 行：domainFilter 写在 early return 之后，会导致白屏`；
还原后复绿。

> **教训**：插件类代码的默认失败模式是「静默不生效」（§13.5），
> 但 **Hook 顺序违规是它的反面——不是静默，是整片炸掉**。
> 两种都需要专门的接线测试，而它们都测不出业务逻辑。

### 17.10 独立审计发现的 3 个高严重度问题（2026-11-06）

派了一个只读审计任务做交叉核对，它找出了我自己审查时漏掉的三处：

**① `stream.ts` 的 return 是逗号表达式 → 记录流丢掉 4 块 UI**

用 TypeScript AST 解析：return 表达式有 4 个操作数，只有最后一个被返回。

| 操作数 | 内容 | 后果 |
|---|---|---|
| #0 | 吞吐 3 格 + 两个筛选下拉 | 求值后丢弃 |
| #1 | toast | 丢弃 |
| #2 | 批量操作条 | 丢弃 |
| #3 | 列表 | **只有这个被返回** |

根因是我上一轮给记录流加「改内容」时多写了一个右括号：内层 div 提前闭合，
后面的块变成逗号表达式的操作数。

**为什么三道防线全没拦住**：`tsc` 完全合法（逗号表达式是合法 JS），
单测只测纯函数，接线测试只查「有没有调用点」。旁证是 `onOpenMemory`
参数从未被使用——TS 的未使用参数检查能提示，但项目没开 `noUnusedParameters`。

修法：修正括号，用 AST 验证 7 个实参各自归位（吞吐 / 筛选 / toast / 批量条 / 列表 / 空态）。

**② frontmatter 写回会静默毁掉手写块列表**

`parse.ts` 要求 `- item` 缩进 ≥2 才认作块列表项。两个后果：

```
输入  tags:
  - 前端
  - 性能   → 写回  tags:
  - value: 前端 性能   （合并成一个对象）
输入  tags:
- a
- b              → 写回  tags: []            （全部丢失）
```

第一条是因为「标量项被包成 `{ value: ... }`，下一个标量项又被当成续行拼进去」。
第二条是因为零缩进（YAML 合法）根本不进块列表分支。

影响面很大：`mergeMeta` / `patchMeta` / `writeBody` 全走这条路，
**`repairMeta` 的 apply 会重写整段 frontmatter**。而 §17.7 写的是
「明确 42 篇正文逐字节比对 0 篇有差异 + 绝不覆盖已有值」——正文确实没变，
但 **frontmatter 里的标签会被毁**，这是当时没验证到的维度。

修法：零缩进也认块列表；标量项不再进「续行」分支；
新增 5 项测试（含往返稳定性断言）。反向验证：恢复旧逻辑，测试精确红在「零缩进块列表」。

**③ 命中率永远算不出正确值：`cite` 全仓无生产写入点**

`hitRate = cite 去重数 ÷ recall 去重数`，但唯一记账调用 `actions.search` 写的是 `kind: 'recall'`。
`kind: 'cite'` 只出现在测试里，真实库 events.jsonl 实测 0 条 cite。
所以命中率恒为 **0**（不是 null）——§11.2 那句「0% 不是算不出」本身就是错的。

修法：给 `memory_recall` 加 `cite: string[]` 参数，模型**真正用过某条记忆后回填**，
此时才记 cite。为什么不搜到就记：搜到 ≠ 用到，若搜到就算命中，
命中率会虚高到接近 100%，这个指标就失去了意义。

### 17.11 同一轮审计的中危修复

| 问题 | 后果 | 修法 |
|---|---|---|
| `last_cited` 只读不写 | `expiryOf()` 永远退回 `updatedAt`，**90 天未被引用机制从未生效** | `recordCite` 在 `kind==='cite'` 时写回 |

### 17.12 把「靠人记得查」变成 CI 级检查

前面的教训都是同一个形状：**缺陷语法合法、单测覆盖不到、只有人工审查能发现**。
而这种保护依赖「谁记得去查」——不可持续。

所以补两层机器检查。

#### 一、更严格的编译器选项

两个包的 tsconfig 开启：

```jsonc
"noUnusedLocals": true,
"noUnusedParameters": true
```

不是洁癖。实测的几次事故里，「有参数但从未接线」恰好是最有价值的旁证：

| 未使用的符号 | 它暗示的真实缺陷 |
|---|---|
| `stream.ts` 的 `onOpenMemory` | return 已变成逗号表达式，4 块 UI 被丢弃 |
| `ProjectPane` 的 `sessionId` | 参数一路传下来但没人用，调用方还写 `sessionId: undefined` |

开启后立刻清出 10 处（core 6 + plugin 4），全部是真实噪音。

#### 二、AST 级静态审计 `scripts/audit.mjs`

`tsc` 看不见「合法但语义错误」的代码，所以用 TypeScript 自己的解析器做语义检查：

| 规则 | 抓什么 | 反向验证 |
|---|---|---|
| `comma-return` | `return a, b, c` 只返回最后一个 | 复现后精确报出 #0~#3 的行号范围 |
| `hook-order` | 组件体里的 hook 写在 early return 之后 | 复现后精确报出「第 114 行写在 early return（第 89 行）之后」 |
| `frontmatter-list` | 块列表解析退化（写回会毁用户标签） | 复现后报出「期望 ["a","b"] 实际 []」 |
| `doc-numbers` | 文档里的测试数与实际不符 | 改成 99 项立刻报错 |

**每条规则都做过反向验证**——一个从不失败的检查等于没有检查。

#### 三、两个设计教训写进了脚本

**① 不许静默跳过。**

frontmatter 检查最初写成 `catch { return }`（动态 import 失败就跳过）。
这意味着它可能在本机从未执行过——而它本该拦住那个数据损坏 bug。
现在加载失败会直接判失败。

**② 规则空转必须被发现。**

新增覆盖度自检：每条规则必须报告「我检查了几个目标」，
任何一个为 0 就直接失败。

```
覆盖度：comma-return=162 hook-order=35 create-element=539 frontmatter=2 doc-numbers=2
```

反向验证：把 frontmatter 用例置空，立刻报「frontmatter 这条检查没有检查到任何目标」。

**③ 文档数字必须真跑测试，不能数 `it(`。**

第一版数 `it(` 字面量，plugin 算出 59 而实际 67——

### 17.14 GUI 真机验证：从「推断」到「看见」（2026-11-06）

前面所有「界面能工作」的结论都是推断——数据层正确 + 结构正确 ≠ 看起来正确。
实测的白屏事故就是反例：数据全对、类型全绿，界面一片空白。

**为什么做不到截图验证（三层原因叠加）**

| 层 | 问题 |
|---|---|
| 浏览器 | GUI 的 URL **不带 token**，直接访问返回 401 |
| 进程 | `desktop` profile 被 Electron 独占，无法自己启动 |
| 信息 | token 只在 `dsh web` 启动瞬间打印一次，之后不再输出 |

**解法**

`web` profile 是独立的、可自由启动的。把它做成专用验证环境：

```bash
dsh --profile web --port 18080 --no-open
# 输出：dsh web: http://127.0.0.1:18080/?token=XXXX
node scripts/shot.mjs --url '<上一步的完整 URL>' --out shots --name home
```

**关键坑**：光把插件装进 `~/.dsh/profiles/web` 的 dependencies **不够**，
还必须列进 `dsh.profile.bundles`，否则宿主不会加载它（桥会返回 `not found`）。
两个都要做。

**产物与用法**

| 文件 | 用途 |
|---|---|
| `scripts/shot.mjs` | 截取运行中的 GUI（支持 `--click` 切分区、`--full` 整页） |
| `~/.dsh/profiles/web` | 验证环境（已装插件；原状备份在 `web.bak-144638`） |

> **为什么这个环境要保留**：它让 UI 回归从此可做。没有它，
> 每次改完界面我只能说「结构上应该对」——这不叫验证。

**本轮实测结果**（截图见 /tmp/shots2）

| 分区 | DOM 特征 | 结论 |
|---|---|---|
| 记录流 | `captureBox=1` | 常驻「记一条」入口已生效 |
| 记忆 | `chips=6` | 状态药丸带计数 |
| 未命中 | `band=5` | 五态计数条 |
