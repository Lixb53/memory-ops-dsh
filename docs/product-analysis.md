## 零、一句话判断

**这不是功能不够，而是「反馈回路一次都没转起来」。**

产品的主线承诺是：agent 搜不到 → 记一条未命中 → 人去补 → 补完能被搜到 → 命中率上升 → 指导下一轮补什么。
实测这条回路在四个环节上各有断裂：

| 环节 | 承诺 | 实测 |
|---|---|---|
| 搜不到 | 记 miss，驱动补齐 | ✅ 记了（13 条事件里有 6 条 miss） |
| 人去补 | 同一 query 攒到 3 次进「等你补」 | ❌ **6 条 miss 全是 `count=1`，`should-fill=0`**——攒不起来 |
| 补完能搜到 | 检索命中即 `recall`，人确认即 `cite` | ⚠️ `recall` 有 2 次，`cite` **0 次**（有记录以来） |
| 命中率指导决策 | 命中率是产品第一指标 | ❌ 显示 **0%**，且它反映的不是检索质量，而是「没人写 cite」 |

> 「攒不起来」不是偶然：`count >= 3` 要求**逐字符相同**的 query（`store.ts:249,259`），
> 而 agent 每次问法都不一样。理论上重复问三遍同样的词能攒到，实践中不会发生——见 §二 断裂 2。

一句话：**仪表盘上最重要的那个数字，从来没有测过它声称在测的东西。**

### 如果只看三件事

| # | 问题 | 一句话 | 详见 |
|---|---|---|---|
| 1 | **检索是 AND，长 query 必然空** | 6 条真实 miss 里 5 条不是「库里没有」，是「检索器不给候选」 | §二 断裂 1、§6.1 |
| 2 | **「90 天未引用」测的不是引用** | 被引用过的条目点「再留 90 天」无效；改任意元数据都会把它清零 | §四 D2 |
| 3 | **最高频条目无法拍板** | `status: active` 的 `INBOX.md` 既不进待办、也没有确认按钮；API 还会报「非法迁移」 | §四 D4 |

> 这三件都在 §九的**第 0 周**，是同一个早上能做完的量。
> 「归档 = 消失」（D1）严重度同样高，但要动 `scan` 契约，排在**第 2 周**（R3），故不进这份「先做三件」。

### 1.2 能力规模

| 项 | 数量 | 证据 |
|---|---|---|
| HTTP 路由 | **34** | `bridge.ts:44-101`（`ROUTES`） |
| 客户端有调用点的路由 | **31** | 静态扫描 `client/**/*.ts` |

**3 条记忆配 34 条路由。** 这个比例本身不是 bug，但它是所有「点进去不知道干什么」的根源——
每个分区都得为「将来数据会多」而设计，而产品第一指标恰恰要求**数据保持少**。

### 1.3 一次「打开总览」到底发生了什么（实测）

`panes/overview.ts:50-59` 挂 4 个 `useBridge`，`panes/maintenance.ts:42-46` 再挂 5 个：

```
overview / snapshot / health / misses          ← 4
verifyAnchor / compact / promote / review / repairMeta  ← 5（5 项维护作业，全是 dry-run 预览）
```

每次打开「总览」= **9 个 HTTP 请求**，其中 **8 个各自 `store.scan()` 一次全库**（只有 `misses` 不扫描）。

本机实测（真实库 3 篇，各跑 20 次取均值；`health` 未单独计时，按同类能力估）：

```
store.scan 4.7ms | snapshot 4.2 | overview 3.7 | review 3.9 | promote 3.4
compact 3.2     | repairMeta 3.2 | verifyAnchor 2.8 | misses 0.5
```

> ⚠️ 这些数字**不能严格相加**：每个能力内部都调用 `scan`，
> 而 `scan` 的独立测量含冷启动，两者口径不同。可信的结论只有两条：
> ① 单个能力都在 **3–4ms** 量级；② 其中**同一批文件的重复读取占绝大部分**。
> 所以九项合计大约 **25–30ms**，不是精确值。

> 这不是性能问题（25ms 无感），**是立场问题**：
> `docs/product.md` §17.1 论证「维护作业按需触发、不加定时器」，
> 而当前实现是「一进总览就全跑一遍」——它比定时器更频繁，只是被叫作「预览」。
> 且这是**唯一随库增长线性变慢的路径**（`docs/product.md` §四 记录过 42 篇真实规模）。

## 二、核心循环诊断：五处断裂

产品的自我进化回路长这样：

```
agent 检索 ──命中──> 读详情 ──用上──> 记 cite ──> 命中率↑
     │
     └─未命中─> 记 miss ──同类攒够 3 次──> 「等你补」 ──人补──> 落库 ──> 下次能命中
```

下面五处，每一处都有代码或实测证据。

### 断裂 1 · 多词检索是 AND 语义，长 query 几乎必然 0 命中

`search.ts:61-67`：`terms.every(...)`——**每个词都必须命中**。

实测 6 条真实 miss query：

| query | 词数 | AND 命中 | 逐词并集 |
|---|---|---|---|
| 记忆库 测试 初始化 | 3 | **0** | 1（`personal.INBOX`） |
| github 仓库 skill preset 配置 管理 | 6 | **0** | 1 |
| 用户偏好 仓库 工具 配置 习惯 | 5 | **0** | 1 |
| dsh 仓库 结构 preset skill 约定 | 6 | **0** | 1 |
| 记忆库 产品 问题 缺口 设计 | 5 | **0** | 1 |
| memory-ops-dsh 产品 架构 结论 | 4 | **0** | 0 |

**6 条里 5 条不是「库里没有」，而是「检索器不肯给候选」。**
agent 的 query 天然是长串关键词（`tools.ts:47` 就写着「可空格分隔多个」），
而 AND 语义让**词越多越搜不到**——这与用户直觉、也与「先用它判断该读哪个文件」的定位直接冲突。

> 口径说明：「逐词并集」是我用 `searchEntries` **逐词单独检索后取 id 并集**得到的，
> 它是「改成 OR 之后大致能出几条」的**近似**，不是 OR 实现后的真实结果
> （真实 OR 会走 `scoreOf` 排序，条数可能不同）。列出来只为说明「候选不是零」。

> `scoreOf()`（`search.ts:95-112`）已经实现了完整的相关度打分（标题 10 / 标签 6 / 正文 2 / pinned +3 / 层加权 / stale 降权 0.4）。
> 也就是说：**能排序的机器已经造好了，却没有东西喂给它**——因为 AND 先把候选全杀光了。

### 断裂 2 · 未命中以「精确字符串」为键，同类问题攒不到阈值

`store.ts:249`：`misses.find(item => item.query === text ...)`——逐字符相等才算同一条。
`store.ts:259`：`count >= 3` 才升 `should-fill`。

于是「记忆库 测试 初始化」「记忆库 产品 问题 缺口 设计」「memory-ops-dsh 产品 架构 结论」
在系统眼里是**三个不相干的问题**，各算 1 次。词序一换、多一个词，就重新计数。

**结果：6 条 miss 全卡在 `observing`，`should-fill = 0`，「等你补」这个分区在真实数据里是空的。**
而它恰恰是产品唯一的「自我进化输入」。

### 断裂 3 · 命中率的分子依赖模型自觉，等于没有

`tools.ts:50-54` 要求模型在读完详情后**回填 `cite: [id]`**，`tools.ts:112-122` 才写 cite 事件。
实测：`recall` 事件 2 条，`cite` 事件 **0 条**。

```ts
// store/stats.ts:121
const hitRate = recalledIds.size === 0 ? null : Math.min(1, citedIds.size / recalledIds.size)
```

数值上它是 `0/2 = 0%`。但真实含义是：**「模型没有回填」**，不是「检索很差」。

这是本产品最贵的一个设计错误：**把一个产品级 KPI 的准确性，押在模型每次记得填一个可选参数上。**
模型的注意力优先给用户的问题，不会给一个「不填也能正常工作」的字段。

> 更麻烦的是：这个 0% 现在被渲染成「命中率 0%」出现在 `project.ts:109-113` 与 `overview.ts:145` 的首屏 KPI 里。
> 用户看到的是「你的记忆库不太好用」，而系统其实在说「我没测到」。

### 断裂 4 · 人的检索与 agent 的检索共用一本账

`panes/memory.ts:100-104`：人每搜一次就走 `search` 且 `record: true`；
`actions.ts:860-873`：命中记 `recall`、未命中记 `miss`。

实测：我在会话里用 UI 检索了一次不存在的词，**立刻多了一条 miss 事件**。

问题有三层：

1. **命中率的口径被污染**。`recall` 本该是「agent 取用过哪些条目」，现在混进了「人手动搜过的词」。分母一变，KPI 就不再是产品主张里那个东西。
2. **人搜不到 ≠ 库里该补**。人可能只是打错字、只是随便看看。这些都会挤进「等你补」的候选池。
3. `recordMiss` 里 `existing.hits = 0`（`store.ts:251`）——**只要人又搜了一次同一个 query，验证期计数就被清零**，
   让「验证生效」这条路更难走到。

### 断裂 5 · 补完之后，没有「它生效了」的证据

未命中流水线最后一态是 `verifying → verified`，靠 `recordVerifyHit` 累计 3 次命中（`store.ts:279-294`）。
但：

- 只有 `verifying` 态的 miss 才会累计；而要进入 `verifying`，得先有人在 UI 里点「生成草稿 → 写结论 → 确认落库」；
- `should-fill` 在当前数据下为空（断裂 2）→ 这条路径**一次都走不到**。

所以「补库」这条链在真实库里是**完整实现、零次执行**。它不是没写，是**没被走到**。

## 三、度量体系：第一指标测错了对象

### 3.1 产品主张 vs 实际开销

`README.md:25-30` 与 `docs/product.md` §三：**第一指标是「常驻前缀 361 tokens / 请求」**，
并给出对照锚点「弃用的 knowledge 曾占 4,120」。

但真实库里：

| 项 | 值 | 说明 |
|---|---|---|
| `billedTokens`（仪表显示） | **171** | 只有 `<available_skills>` 框架；catalog = 0 |
| `resident.state` | **`empty`** | 本机 `~/.dsh/skills` 不存在，一个 skill 都没有 |
| **插件自己的两个工具定义** | **≈ 675 tokens**（`estimateTokens` 粗算：说明 109+126 + 参数 schema 148+212 + 每工具约 40 的包装；**未实测**） | `tools.ts:36-296` |

也就是说：**这个插件每请求真实付出的固定开销，比它显示的 171 大 4 倍左右；
而它显示的 361 依赖的两个 `*-memory` skill，在本机根本不存在。**

> 这不是「数字算错了」，是**测的对象错了**：
> 仪表的锚点是「skill description」（一个已经决定不做的机制），
> 而真正的固定成本是「两个工具的 name + description + JSON Schema」——
> 它们每请求都在，且随参数增多而变大。
>
> 一个以「成本可见」为第一主张的产品，**看不见自己最大的那笔成本**。

> 还有一层更细的口径问题：`SKILL_CATALOG_FRAME_TOKENS = 171` 被定义为
> 「`<available_skills>` 目录的固定框架、与 skill 数量无关」（`actions.ts:38-44`）。
> 而本机 `resident.state = 'empty'`——**一个 skill 都没有**。
> 既然没有目录，这 171 的框架是否还真的被注入？我没有宿主的计量接口，**无法确定**。
> 若答案为否，那么仪表显示的不是「偏小」，而是**凭空多算了一笔**。
> 这正说明：**成本数字必须是测出来的，不能是常量拼出来的。**

### 3.2 三个数字的命名仍然会误导

`overview.ts:130-147` 已经把「每请求成本 / 索引体积」拆成两格，这是对的。
但 `project.ts:116-119` 那一格仍叫「本项目索引」，量的是 `layers.l0.tokens`；
真实库里所有条目 `layer` 都是 `l2` → 该格实测为 **0**。首屏出现一个 `0`，
用户无法判断是「本库没有索引层文件」还是「没测到」。

### 3.3 统计口径把最贵的那条漏掉了

真实库里 `personal/INBOX.md` 的 `status` 是 `active`（老数据，不在 `CONFIDENCE_STATES` 枚举内）。
`store/stats.ts:152` 的 `counts.pending` 只数 `hypothesis|observed`；
`confirmed / rejected / stale / archived` 也都不含 `active`。

于是：**全库最常用的那个文件，在每一个计数里都不存在。**
它不进「待你处理」，不进「已确认」，`confirmRate` 的分母也不算它（实测 `confirmRate = 1` 是由 1 条 confirmed 算出来的）。

## 四、六个高危产品缺陷 + 一个待验证观察

> 判定标准：**用户会因此做错决定，或相信一个假的结论。**
> D1–D6 **全部在临时目录里用真实 API 复现过**，不靠读码猜测；
> D7 例外——它只有构造数据上的表达式验证，**尚未目视复现**，故降级为「待验证观察」，不计入高危六项。

### D1 · 归档 = 从库里消失，且「已归档」结构上取不到东西

- **证据**：`store/io.ts:74` `listMarkdown` 在根层跳过 `archive/`；`archiveEntry`（`store.ts:642-666`）把文件 `move` 到 `archive/<date>/...`。
- **实测**（临时库，1 条记忆）：归档后 `scan()` 条目数 1 → **0**；检索该条目 **0 命中**；
  `counts.archived = 0`；`expireRate = null`（因为分母也变成 0 了）。
  在真实库（3 条）上则表现为**分子被悄悄扣掉**：归档 1 条后 `expireRate` 的分母变 2、分子不算它，
  数字看起来正常，但它统计的已经不是真实现象。
- **影响**：
  1. 「到期退役」是三条产品主张之一，而它的出口是**删除**。人拍板退役后，**再也看不到自己退役了什么**。
  2. `memory.ts:147` 的「已归档」筛选**在结构上取不到东西**（`scan` 不含 `archive/`）；`overview` 的「过期率」口径是 `(stale + archived) / 总条目`（`store/stats.ts:132-135`），
      其中 **archived 恒为 0**——它只能反映「待复核」，无法反映「已退役」。
  3. 与「可撤销、可审计」立场冲突：`archive` 事件里只有 `path`，而条目已经不在 `scan` 结果里，**没法还原**。
- **修法**：`archive/` 不是垃圾桶，是**一个可见的状态**。两个选择：
  - 最小改动：`scan()` 增加 `includeArchived`，`listMarkdown` 不跳过 `archive/` 根，条目按 `status: archived` 参与统计但**不参与检索与队列**；
  - 结构性改动：见 §五 R3。

### D2 · 「再留 90 天」对**被引用过**的条目完全无效；而任意一次改元数据都会把「90 天未引用」清零

- **证据**：`expiryOf`（`schema.ts:346-355`）判定顺序是 `lastCitedAt ?? updatedAt ?? createdAt`；
  而 `keepLonger`（`store.ts:668-671`）只写 `updated`。
- **实测**：一条 `last_cited = 2026-01-01` 的条目，点「再留 90 天」后 → `lastCitedAt` 仍是 2026-01-01，
  `expiry = { level: 'retire', days: 320 }`。**按钮点了，条目仍然判退役。**
- **影响**：这是「到期退役」的**唯一人工出口**。它恰好在「这条记忆被频繁使用」时失效——
  也就是最不该被退役的那些条目。用户会看到「已再留 90 天」的成功提示（`project.ts:321-323`），然后条目继续出现在退役队列里。
- **注意「完全无效」的边界**：只有**带 `last_cited`** 的条目会这样。一条从未被 cite 过的条目，
  `expiryOf` 会退回 `updatedAt`，而 `keep` 确实刷新了它——所以那条路径是有效的。
  换句话说：**失效的恰好是「真的在被用」的那批**，这也解释了为什么它一直没被发现（真实库里目前 `cite` 事件为 0）。
- **修法**：`keepLonger` 同时写 `last_cited`（语义：人确认它仍然有效，等同于一次引用）；
  或让 `expiryOf` 优先取三者中**最近**的时间，而不是按固定优先级回退。
- **同源的第二个问题（实测确认）**：`patchMeta`（`store.ts:384-398`）**无条件写 `updated`**。
  于是任何一次元数据修改——包括「确认」一条 300 天没动过的记忆——都会把它重新算成 `fresh`（0 天）。
  实测：`updated: 2026-01-01` 的条目改一个无关字段后，`expiry` 从 `retire/320天` 变成 `fresh/0天`。
  **「90 天未被引用」这个机制测的不是「被引用」，而是「最后一次元数据写入」**——
  与 `recordCite` 注释里那段「早先只 append 事件、从不写 last_cited」的自我批评是同一个 bug 的另一半：
  那次修的是「引用不刷新时间」，这次是「不引用也刷新时间」。
  > 注：`mergeMeta`（`store.ts:360-381`）不写 `updated`，所以 `repairMeta` 走的是安全路径——
  > 实测修补一条 320 天条目后 `expiry` 仍是 `retire/320天`。**问题只出在 `patchMeta` 这条路径上。**
- **修法（合并）**：`expiryOf` 改取 `max(lastCitedAt, updatedAt, createdAt)`，
  并把「人主动延长/确认」建模成一条**显式事件**（`keep` / `confirm`）而不是靠 `updated` 顺带生效。

### D3 · 「撤销驳回」把条目伪造成「较可信」，且被驳回的条目仍躺在待办里喊「推断待确认」

- **证据**：`actions.ts:993-996` `undoReject` 直接把状态写成 `'reinforced'`（置信 0.7），且不清 `refuted_at`。
- **这是刻意设计，不是笔误**：`packages/core/test/actions.test.ts:189-190` 明确断言
  「驳回 → 撤销 → `status === 'reinforced'`」。也就是说**有人把这个行为写进了回归测试**，
  它会一直被保护下去——所以修它必须先改测试，这比修 bug 更需要先说服人。
- **实测**：`hypothesis(0.3)` → 驳回 → 撤销 → 实际状态 **`reinforced` / 0.7 / `refuted_at` 仍残留**。
- **影响**：`reinforced` 在状态机里的含义是「跨 ≥3 个不同会话被引用且无反驳」（`schema.ts:270-277` `REINFORCE_MIN_SESSIONS`）。
  撤销一次驳回，就凭空造出了一段**从未发生过的证据累积**。
  这正是产品反复强调「不许伪造历史」的反面（`schema.ts:128`: 「人不能把 confirmed 降级成 hypothesis（那是伪造历史）」）。
- **附带**：被驳回的条目仍进 `queue`（`needsDecision` 在 30 天内返回 true），
  而队列项的 `kind` 由到期分级算出 → `kind = 'confirm'`、`reason = '推断待确认'`（`actions.ts:350-371`）。
  实测队列项：`{ status: 'rejected', kind: 'confirm', reason: '推断待确认' }`。
  **界面在对一条已驳回的条目说「推断待确认」，并给出「确认」按钮**（点了会静默翻案）。
- **修法**：`undoReject` 回到驳回前的状态（把原状态记进 `refuted_from`）；
  队列对 `rejected` 用独立的 `kind: 'undo-reject'` 与独立文案。

### D4 · 老数据（`status: active`）的条目无法拍板：API 报「非法迁移」，界面上则根本没有按钮

- **证据**：`schema.ts:383-392` `canHumanTransition` 对未知状态回退到自动表，而 `STATE_TRANSITIONS['active']` 是 `undefined` → 返回 false。
  更值得注意的是 `schema.ts:387-390` 的注释**明确写了这条兜底的目的**：
  「非枚举状态（老数据里的 `active`）先按自动表放行 …… 在这个窗口期里不该让用户点不动按钮」。
  **但兜底本身失效了**：它转去查 `STATE_TRANSITIONS['active']`，那里同样是 `undefined`，
  于是「放行」变成了「一律拒绝」。注释承诺的事，代码没做到——这类「注释比实现乐观」的地方，
  比没有注释更难查。
- **实测**：`confirm` → `{ ok: false, error: '非法状态迁移：active → confirmed' }`；`reject` 同样失败。
- **影响**：真实库里 `personal/INBOX.md`（178 tokens，全库最大的日常文件）就是 `active`。
  **它在界面上没有任何可用的拍板出口。** 与 `docs/product.md` §18.2 记的「确认按钮必然失败」是同一族问题
  （都是「界面提供的动作与状态机不一致」），但方向相反：
  那次是**按钮在、点了必败**；这次是**按钮根本不在**——更难发现，因为屏幕上没有报错。
- **注意边界**：`memory.ts:455` 的「确认」按钮只在 `stale | observed | hypothesis` 三态渲染，
  所以 `active` 条目在**详情页**看不到确认按钮；但「待处理队列」走 `snapshot.queue`，
  而 `needsDecision` 对 `active` 返回 false → 它也不进队列。
  **所以真实表现不是「按钮报错」，而是更安静的：这条最常用的文件既不在队列里，也没有可点的出口**——
  它卡在「已确认」与「待确认」之间，任何一格都不算它。这比报错更难发现。
- **修法**：`repairMeta` 已经能纠正 `active`（`maintenance.ts:626-634`），但它藏在「总览 → 维护作业 → 补全元数据」里。
  正确做法是**在读取层归一**：`readEntry` 把非法 `status` 归一为 `hypothesis`（并标 `statusRaw`），
  维护作业只负责**把文件改对**，不负责**让界面能用**。

### D5 · 捕获不分域：所有写入口硬编码 `personal`

- **证据**：`capture-tab.ts:35,140,144`、`remember.ts:253,259`、`stream.ts:46,82,103,220,226,232,275,283,290,296`
  ——**共 15 处硬编码 `domain: 'personal'`**（`grep "domain: 'personal'"` 实测）。
- **影响**：产品主张「两域物理隔离：工作会话不加载个人档案」（`README.md` / `product.md` §四）。
  但**在工作会话里记的任何东西，都进个人 INBOX**。
  隔离只发生在「读」，没发生在「写」——而写错了的那条，之后再也回不到工作域（没有跨域移动能力）。
  `git log` 里那条 `docs: 澄清 remote 与目录名的职责，并记录捕获不分域的缺口` 说明这一点已被记录，但**未修**。
- **修法**：捕获入口按当前 `cwd` 解析出的 project 决定 `domain`；无法解析时**显式让用户选**（而不是默认 personal）。

### D6 · 隐私闸门会拦住「最该被记住的那类内容」

- **证据**：`privacy.ts:30` 把 `10.x / 172.16-31.x / 192.168.x` 一律判为敏感；`writeBody`（`actions.ts:922`）与 `missConfirm`（`actions.ts:1153`）都走这道闸门。
- **影响**：这是一套**记录技术结论**的系统。而「内网 IP 段怎么配」「网关是 192.168.x.x」正是它该记的内容。
  实测三条样本：`游戏服网关是 192.168.1.10，内网段 10.0.0.0/8` → `blocked: true（内网 IP ×2）`；
  `部署在 172.16.32.5 上` → `blocked: true`；`password: hunter2abc` → `blocked: true`。
  结果是：写架构结论时被拦、写复盘时被拦，用户唯一的办法是把内容改得**更含糊**——
  这与「人可审的精确台账」直接冲突。
- **修法**：分级而非一刀切。`block` 只留给**凭据类**（密钥 / 私钥 / 身份证 / `password=` 赋值）；
  内网 IP 降级为 `warn`（提示但不拒写），并给「这条要进库吗」的单次豁免——**豁免要留审计**。

### D7（待验证观察，非高危缺陷）· 队列排序按「未引用天数」降序，而它想表达的是「紧急度」

> **降级说明**：D7 未在真实队列上目视复现，证据只有排序表达式本身 + 构造数据。
> 它不计入 D1–D6 那六个「已复现」的高危缺陷，仅供参考；若按此修，请先补实测。


- **证据**：`actions.ts:371` `sort((a,b) => (b.days ?? 0) - (a.days ?? 0))`。
- **实测**：一条刚建（0 天）的推断与一条老条目（0 天）排序时纯靠插入顺序；`keep` 会刷新 `updated` → 点过「再留 90 天」的条目**自动沉到队尾**。
  （我只在构造数据上验证了排序表达式本身，**没有**构造出「天数差异明显」的两条来目视队列——
  因为 `days` 来自 `lastCitedAt ?? updatedAt ?? createdAt`，而新建条目都是 0 天。这条结论强度弱于 D1–D4。）
- **影响**：待办队列是首屏唯一的行动入口。它的顺序直接决定用户先处理什么。
  「按未引用天数」对「推断待确认」这类条目**没有信息量**（它们的 `days` 基本都是「距上次编辑」）。
- **修法**：按 `kind` 分层（到期 > 锚点失效 > 待确认），层内按「证据强度」而非天数。

## 五、需要重构的点（产品视角，不是代码洁癖）

> 排序依据：**不改它，产品主张就说不通。**

### R1 · 失败只有一种形状 → 界面无法告诉用户「怎么办」

> **状态更新（2026-11-17 19:27 复核）**：这一条正在被修复，但**只修了一半**。
> 仓库里另一个会话已落地 `actions/errors.ts::classifyError`，`guard`(`actions.ts:100`) 现在会返回可选的 `kind` 与 `hint`。
> 但客户端 `client/**/*.ts` 里 `error.kind` / `failure.kind` 的消费点仍然是 **0**——
> 界面照旧只显示 `error` 字符串。**剩下的是接入，不是设计。**

文档写作时看到的原始形态是：`guard` 把 34 个能力的所有异常压成 `{ ok: false, error: string }`。
后果在界面上的表现是具体的：

- 隐私拦截（该给「填脱敏版本」）、状态迁移非法（该给「可用状态」）、锁超时（该给「重试」）、文件不存在（该说「可能已被改动」）**在类型上完全一样**；
- 前端只能把 `error` 原样贴出来（`project.ts:262`、`memory.ts:178`、`overview.ts:87` 都是这个形态）；
- 于是「错误提示告诉用户如何解决」这条要求，**在架构上做不到**——信息在进入字符串那一刻就丢了。

**这是产品级重构，不是代码整理。**（`architecture-review.md` §二 给了拆法，此处补产品侧的必要性：
拆分的价值不在文件变短，在于 `kind: 'blocked' | 'invalid-state' | 'conflict' | 'io' | 'not-found'` 能让 UI 分叉。）

**接入的最小成本**（给执行者）：`api.ts::call()` 抛出的 `BridgeError` 只带 `message` 与 `route`，
需要把桥返回的 `kind` / `hint` 带进 `BridgeError`，再由 `ErrorState` 按 `kind` 选文案与按钮。
这是纯前端改动，不需要再动 core。

### R2 · 「按需触发」被实现成了「打开页面就全跑」

见 §1.3。五项维护作业在 `panes/maintenance.ts:42-46` 无条件 `useBridge`，
而 `MaintenancePanel` 是在 `overview.ts:284` **无条件挂载**的（不在任何 `open` 分支里），
所以面板收起时那 5 个请求**已经发出去了**。
这与 `maintenance.ts:6-8` 自己写的「低频、按时做一次」正好相反。

**重构方向**：展开某一行时才发那一条请求（`open !== null` 才挂 `useBridge`），
并把 `dry-run` 结果**按作业分别缓存一次会话**（切页签回来不重跑）。

### R3 · 归档区需要成为一等产品对象，而不是被跳过的目录

见 D1。现在 `archive/` 在 `scan` 层被摘掉，导致：

- 「已归档」筛选始终为空；
- 过期率里 `archived` 那一项恒为 0（只剩 `stale` 在起作用）；
- 退役不可见、不可撤销、不可审计。

**重构方向**：`scan` 支持 `includeArchived`，返回 `archived: true`；
`snapshot` 默认不含、`memory` 的「已归档」筛选显式含；检索默认排除、但允许 `include: 'archived'`。
这一步同时修好 D1 与「退役率」这个唯一能防止产品腐化的指标。

### R4 · 事件流无上限，且 `slice(-200)` 在解析之后

`store.ts` 的 `readEvents` 读全文并全量 `JSON.parse`；`actions.ts:1297-1302` 先拿全量再 `slice(-200)`。
`events.jsonl` 是唯一**没有保留策略**的数据结构，而产品主张是「按需加载」。

**重构方向**：`readEvents({ limit })` 从尾部反向读；中期按月分片（见 `architecture-review.md` §四）。
产品侧的理由：**三率只看 30 天、复盘只看 7 天，它们本来就没有理由读全量。**

### R5 · 34 条路由 / 5 个分区 / 3 条数据：先做「最小闭环」

`bridge.ts` 有 34 条能力，其中 `index` 与 `setStatus` **没有任何界面入口**（静态扫描确认），
`healthCheck` 是给诊断用的（合理）。也就是说：**能力比入口多，入口比数据多。**

产品侧的主张不是删能力，而是：**先让一条链子完整跑通，再铺第二圈。**
推荐先跑通这条（它只需要 3 条能力）：`search`（OR + 打分）→ `miss` 聚类 → `missConfirm` → `recordVerifyHit`（**自动**）→ 命中率**真实**上升。

### R6 · 检索记账口径必须人机分离

见 §二 断裂 4。`search` 的 `record` 参数把「agent 的取用」与「人的查找」写进同一本账。

**重构方向**：事件加 `actor: 'agent' | 'ui'`；`hitRate` 只统计 `actor = 'agent'` 的 recall/cite；
人的检索可以记（它对「人关心什么」有价值），但**不进命中率，也不写 miss 表**。

### R7 · `actions.ts` 单闭包（写作时 1653 行；重构进行中）与一个真实的口径 bug

### 6.1 但第 1 条有一个必须先想清楚的副作用（重要）

**把 AND 改成 OR，会让「未命中」这个信号大幅减少——而它正是产品的自我进化输入。**

现在的逻辑是：`matched = hits.length > 0`（`actions.ts:861` 起的 `if (record)` 块用 `result.matched`），
不命中就写 miss。改 OR 之后，只要**任何一个词**在库里出现过，`matched` 就为 true，于是：

- `misses.json` 几乎不再增长；
- 「等你补」几乎不再出现——**从「结构上到不了阈值」变成「结构上没有候选」**；
- recall 分母会从当前的 2 涨到 N。**但注意**：在 `cite=0` 的真实库里，`hitRate` 的分子恒为 0
  （`store/stats.ts:121`：`citedIds.size / recalledIds.size`），所以它**不是「更低」，而是恒为 0**——
  分母再大也一样，直到有人回填 `cite`。这点反而削弱了「改坏命中率」的担忧，
  但**没有削弱**上面两条关于 miss 信号的担忧。

也就是说：**单独改 OR，会把断裂 1 修成断裂 2 的另一个版本。**

**正确的改法是同时引入「相关度地板」，把三种情况分开：**

| 情况 | 判据 | 记账 |
|---|---|---|
| 强命中 | 最高分 ≥ 阈值（例如 ≥ 10，即标题/标签命中） | `recall` |
| 弱命中 | 有候选但最高分 < 阈值 | `recall` + **`miss`（带 `weak: true`）** |
| 无候选 | 0 条 | `miss` |

这样「搜到一堆不相干的」也会留下补齐信号，而且信号质量比现在高——
它记录了「问的是什么、为什么没找到有用的」。

> 阈值本身是产品判断，不该拍脑袋定。建议先用真实数据跑一遍分布再定，
> 并把阈值写进 `schema.ts`（与 `STALE_WEIGHT`、`REINFORCE_MIN_SESSIONS` 同级），
> 而不是散在 `search.ts` 里。

### 6.2 第 3 条也有一个连带影响

把 `active` 归一成 `hypothesis` 之后，`personal/INBOX.md` 会**立刻出现在待办队列里**（`needsDecision` 对 hypothesis 返回 true）。
这是对的——它确实是一条没拍过板的记录。但要同步确认：
`memory.ts:146` 的「已确认」筛选把 `active` 与 `confirmed` 视为一组，
归一之后那一格计数会**减少 1**，需要在同一批改动里一起对账，否则会留下「数字对不上」的新问题。

## 七、信息架构层面还缺一块：**档案**

已有 v4 方案（`design/information-architecture.md`）把 5 个数据分区改成 5 个任务入口：
**今天 / 记一条 / 待办 / 记忆 / 库健康**。这个方向我认同，但**它没有「归档」的位置**：

- 到期退役的动作发生在「待办」，退役结果**没有去处**（`已归档` 筛选过滤的是一个取不到东西的集合，见 D1）；
- 「库健康」谈成本，「记忆」谈现存，**没有任何一页回答「我退役过什么、对不对」**。

**建议**：不新增第 6 个页签，而是在「记忆」页加一个**状态筛选 `已归档`**，
并让它真的能查出东西（依赖 R3）。理由：
归档条目是**低频查看、必须可查**的对象——它不该占一级导航，但不能不存在。
这也符合 v4 自己定的原则：「一个动作只有一个入口，但结果必须可见」。
