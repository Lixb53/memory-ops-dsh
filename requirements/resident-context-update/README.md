## 一分钟结论

三条诉求背后是同一个缺口：**常驻前缀只有一个数，没有"条目"这个概念**。

- 现在：`总览 → 常驻前缀 229`，构成面板只有三行（skill description / 框架 171 / 置顶聚合 1 条）。
- 缺的是：**逐条**（哪几条置顶、各多少 tokens、哪条被跳过）、**第四个桶**（两个工具的 schema，每请求都在）、**可编辑入口**、**"改了什么"**。

本次不新增一级分区，全部落在 `health`（库健康）里：成本区 → 明细 → 编辑二级页；版本卡 → 差异 + 去宿主页更新。

**3.3 已按新证据修正**：宿主插件页自己就有「版本」区块（可更新到 X · 发布于 Y · N 个新版本 · 重新检查），
并内置热更新与失败回滚。所以我们**不自建更新执行**（R22/R24），只补宿主不给的**提交差异**。

**并且已实测出关键约束**：宿主对 `git` 安装（含打了 tag 的）在查 registry 之前就判 `not-updatable`，
`link` 则无版本可比——**只有发布到 npm 才能拿到那块"可更新到"**。
详见 [`research/host-version-block-verification.md`](research/host-version-block-verification.md)。
所以在发 npm 之前，3.3 的实际形态是：宿主显示"失败 + 英文原因"，我们把它翻译成人话 + 给命令。

## 需要你拍板的两件事（其余可"都按推荐"）

1. **Q5 / A7**：注入段里那句"另有 N 条超出 256 tokens 预算未注入"，我建议**从系统提示词里移除**（改为界面展示）。
   理由是它每变一次就作废一次前缀缓存（本仓实测单次 20–57 万 tokens）。**这是行为变更**，需要你点头。
2. **Q14 / A19**：要不要把插件**发到 npm（或至少打 git tag）**。宿主版本区块只对有"可比较版本"的安装源工作；
   维持 git 直装 + 裸 commit，3.3 可能永远停在 `command-only`（只能复制命令）。
3. **Q15 / A20**（新增）：是否接受"**我们不做更新执行、只补差异**"。接受的理由：宿主已有热更新 + 失败回滚，
   两个入口并存会让"谁回滚、回到哪一版"无法判断。
